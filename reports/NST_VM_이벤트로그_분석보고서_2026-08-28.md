## 2. 이벤트별 상세 분석

### 2.1 Wininit 15 (경고) — VBS/Credential Guard 미기동 ★핵심
> "Credential Guard 및/또는 VBS 키 격리가 구성되었지만 보안 커널이 실행되고 있지 않음"

- **원인**: Windows 11 25H2는 기본적으로 VBS(가상화 기반 보안)를 활성화하려 하나, KVM/QEMU 게스트에 중첩 가상화(nested virtualization)가 노출되지 않아 보안 커널을 기동하지 못함.
- **조치 (택1)**:
  1. **VBS 비활성화 (권장, VM 성능 향상 효과)**:
     ```
     bcdedit /set hypervisorlaunchtype off
     ```
     재부팅 후 `msinfo32`에서 "가상화 기반 보안: 사용 안 함" 확인.
  2. VBS가 필요하면: libvirt에서 CPU `host-passthrough` + VMX/SVM 노출 + Hyper-V enlightenments 구성.

### 2.2 TPM-WMI 1801 / 1025 (오류) — Secure Boot 2023 인증서 미적용 ★핵심
> "업데이트된 보안 부팅 인증서는 이 디바이스에서 사용할 수 있지만 아직 펌웨어에는 적용되지 않았습니다"

- **원인**: Microsoft의 Secure Boot 인증서 세대 교체(2011 CA → 2023 CA, CVE-2023-24932 대응) 과정에서, 현재 펌웨어 버전인 Debian OVMF `2025.02-8`에는 2023 인증서가 미포함(Debian 버그 #1134793).
- **버전 현황**:

  | OVMF 버전 | 2023 인증서 | 비고 |
  |---|---|---|
  | `2025.02-8+deb13u1` (현재) | ❌ 미포함 | Debian 13 Trixie stable 기본 |
  | `2025.11-5` 이상 | ✅ 포함 | **권장 버전** (sid/testing, 백포트 진행 중) |
  | (참고) Proxmox `pve-edk2-firmware-ovmf ≥ 4.2025.05-1` | ✅ 포함 | Proxmox 계열 해결 버전 |

- **조치 (호스트에서)**:
  1. Trixie 포인트/보안 업데이트 확인: `apt update && apt list --upgradable | grep ovmf` → `deb13u2` 이상 백포트가 있으면 적용.
  2. 없으면 backports/testing에서 설치: `apt install -t trixie-backports ovmf`
  3. **중요**: OVMF_CODE 교체만으로는 부족. 기존 VM의 NVRAM(VARS 파일)에 옛 키가 남아 있으므로, 최신 `OVMF_VARS_4M.ms.fd` 템플릿으로 nvram 재생성 필요.
  4. 게스트 확인: `mokutil --db --short`에 `Windows UEFI CA 2023` 표시되면 완료.
- **시급성**: 기존 2011 인증서가 2026년 6월~10월에 걸쳐 만료. VM을 계속 운영할 예정이면 **가까운 시일 내 업데이트 권장**. (당장 부팅/운영 장애는 없음)

## 4. Secure Boot 인증서 관련 상세 (Debian 버그 #1134793)

### 4.1 버그 내용
- 제목: **"ovmf: Secure Boot keys will expire in June 2026"**
- 요지: Debian 13 (Trixie) stable의 `ovmf 2025.02-8+deb13u1`에는 Microsoft 2011 인증서만 내장되어 있고 2023 신규 인증서가 없음. 2011 인증서는 2026년 6월~10월 순차 만료 예정(CVE-2023-24932 "BlackLotus" 부트킷 대응 세대교체)이므로 stable에 백포트 요청.
- 코드 결함이 아니라 **"stable 패키지에 최신 인증서 미포함" 패키징 이슈**.

### 4.2 이벤트 문구 해석 (TPM-WMI 1801)
> "업데이트된 보안 부팅 인증서는 이 디바이스에서 **사용할 수 있지만** 아직 펌웨어에는 적용되지 않았습니다"

- "사용할 수 있다" = Windows(OS)가 Windows Update로 새 인증서 데이터를 **보유**하고 있다는 뜻
- "펌웨어에 적용 안 됨" = 펌웨어(OVMF)의 Secure Boot DB에 **기록하지 못했다**는 뜻
- 즉 인증서를 가진 쪽은 Windows이고, OVMF 펌웨어에는 없는 상태.

### 4.3 인증서 적용 여부 확인 방법

**① Windows 게스트 안에서 (관리자 PowerShell) — 권장**
```powershell
# Secure Boot 활성화 여부
Confirm-SecureBootUEFI

# DB에 2023 인증서 존재 여부 (True = 적용됨)
[System.Text.Encoding]::ASCII.GetString((Get-SecureBootUEFI db).bytes) -match 'Windows UEFI CA 2023'

# KEK에 2023 키 존재 여부
[System.Text.Encoding]::ASCII.GetString((Get-SecureBootUEFI KEK).bytes) -match 'KEK 2K CA 2023'
```
> `Get-SecureBootUEFI`가 "지원되지 않는 플랫폼" 오류 시 → 해당 VM은 Secure Boot 미사용(레거시 부팅 또는 non-secboot OVMF)이며, 이 경우 TPM-WMI 1801은 실질 영향 없음.

**② KVM 호스트에서 VM의 VARS 파일 직접 검사**
```bash
# nvram 경로 확인
virsh dumpxml <VM이름> | grep nvram

# 2023 인증서 문자열 검색 (출력 있으면 적용됨)
strings /var/lib/libvirt/qemu/nvram/<VM이름>_VARS.fd | grep -i '2023'
```

**③ 리눅스 게스트인 경우 mokutil**
```bash
mokutil --kek | grep Subject:
mokutil --db  | grep Subject:
```
- `--short` 옵션은 mokutil 0.7.x 이상에서만 지원 → 구버전에서는 위처럼 grep 사용.
- ⚠️ mokutil은 리눅스 전용이며, **실행한 머신 자신의** UEFI 변수를 읽음. 호스트에서 실행하면 호스트 펌웨어 상태이지 VM 상태가 아님. Windows에는 존재하지 않는 명령.

**확인할 인증서 이름:**
| 위치 | 구 키 (만료 예정) | 신 키 (목표) |
|---|---|---|
| KEK | Microsoft Corporation KEK CA 2011 | Microsoft Corporation KEK 2K CA 2023 |
| DB | Microsoft Windows Production PCA 2011 | Windows UEFI CA 2023 |

### 4.4 해결 절차 (호스트)
1. Trixie 백포트 업데이트 확인: `apt update && apt list --upgradable | grep ovmf` (`deb13u2` 이상이면 적용)
2. 없으면: `apt install -t trixie-backports ovmf` (또는 testing의 `2025.11-5` 이상)
3. **필수**: OVMF_CODE 교체만으로는 부족 — 기존 VM NVRAM(VARS)에 옛 키가 남아 있으므로 최신 `OVMF_VARS_4M.ms.fd` 템플릿으로 nvram 재생성
4. 게스트에서 위 4.3 방법으로 `Windows UEFI CA 2023` 확인되면 완료

### 4.5 호스트가 Debian 11 (Bullseye)인 경우

**현실:**
- Bullseye 기본 `ovmf`는 `2020.11` 계열 — 2023 인증서 없음.
- `bullseye-backports`는 이미 종료 (2024-08 LTS 전환 이후 신규 업데이트 중단) → backports로는 해결 불가.
- Bullseye LTS 자체도 2026-08 종료(EOL) 상태.

**해결 방법 (권장 순):**

**방법 1 — 호스트 업그레이드 (근본 해결, 운영 지속 시 권장)**
- Bullseye → Bookworm(12) → Trixie(13) 순차 업그레이드 후 4.4 절차 적용.
- 호스트가 EOL이므로 보안 관점에서도 필요.

**방법 2 — VARS에 2023 인증서 수동 주입 (업그레이드 곤란 시 권장, 가장 외과적)**
```bash
pip install virt-firmware   # bullseye 저장소에 없으므로 pip 사용

# VM 종료 후 실행
virt-fw-vars --input  /var/lib/libvirt/qemu/nvram/<VM>_VARS.fd \
             --output /var/lib/libvirt/qemu/nvram/<VM>_VARS.fd.new \
             --add-kek  MS-KEK-2023.pem \
             --add-db   MS-UEFI-CA-2023.pem
mv <VM>_VARS.fd.new <VM>_VARS.fd
```
- 인증서 PEM: Microsoft 공식 저장소 `github.com/microsoft/secureboot_objects`
  (`Microsoft Corporation KEK 2K CA 2023`, `Windows UEFI CA 2023`)

**방법 3 — 신버전 OVMF 바이너리만 추출 사용**
```bash
dpkg-deb -x ovmf_2025.11-5_all.deb /opt/ovmf-new/
# libvirt XML의 <loader>/<nvram> 경로를 /opt/ovmf-new/... 로 변경
```
- OVMF는 의존성이 거의 없는 펌웨어 이미지라 실무적으로 가능.
- ⚠️ 기존 VM은 VARS를 새 템플릿으로 재생성해야 하며 Secure Boot 키가 초기화됨 → **BitLocker 사용 중이면 복구 키를 반드시 사전 확보**.

### 4.6 동일 구성 정상 단말과의 비교 분석 (2023 인증서 누락 원인)

**관측 사실 (2026-08-28 15:41 확인):**
- 정상 단말: PowerShell 검사 `True` — DB에 `Windows UEFI CA 2023` 적용됨
- 호스트 OVMF 버전: `2025.02-8+deb13u1+grm3u2` — **이슈 단말과 동일**
- 정상 단말 호스트에 `python3-virt-firmware (24.11-2+grm3u1)` 설치 확인

**핵심 결론:**
OVMF 패키지 버전이 같은데 결과가 다름 → 원인은 펌웨어 코드(OVMF_CODE)가 아니라 **VM별 NVRAM(VARS 파일) 상태 차이**. Secure Boot 인증서는 VM마다 존재하는 VARS 파일에 저장되므로, 같은 호스트·같은 패키지라도 VM별로 다를 수 있음.

**정상 단말에 인증서가 적용된 경로 (가능성 순):**
1. **Windows Update의 펌웨어 DB 직접 기록 성공** (가장 유력) — CVE-2023-24932 대응 배포. 레지스트리 `AvailableUpdates` 플래그 트리거 + UEFI 변수 쓰기 + 정상 재부팅 완료 필요. 이슈 단말의 TPM-WMI 1801은 이 과정이 미완료라는 상태 보고.
2. **VARS 생성 시점/템플릿 차이** — `+grm3u2` suffix는 벤더 커스텀 빌드로 보이며, 정상 단말이 2023 키 포함 템플릿으로 생성됐을 가능성.
3. **virt-fw-vars 수동 주입** — python3-virt-firmware는 기본 설치 패키지가 아니므로 벤더/운영자가 수동 주입했을 가능성.

**이슈 단말에서 확인할 항목:**
```bash
# 호스트: 두 단말 VARS 파일 비교
strings <VM>_VARS.fd | grep -i "2023"     # 이슈 단말: 없을 것으로 예상
ls -l <VM>_VARS.fd                         # 크기/수정일 비교
virsh dumpxml <VM> | grep -A2 loader       # loader/nvram 템플릿 경로 비교
```
```powershell
# 이슈 단말 Windows: 배포 상태 확인
reg query HKLM\SYSTEM\CurrentControlSet\Control\SecureBoot /v AvailableUpdates
Get-WinEvent -LogName System | Where-Object {$_.Id -in 1795,1796,1797,1801} | Select -First 10
```

**조치 제안 (정상 단말과 동일 상태로 맞추기):**
1. 이슈 단말 Windows에서 인증서 배포 재시도 트리거:
   ```powershell
   reg add HKLM\SYSTEM\CurrentControlSet\Control\SecureBoot /v AvailableUpdates /t REG_DWORD /d 0x40 /f
   ```
   이후 재부팅 2회 → PowerShell 검사로 `True` 확인.
2. 실패 시: 호스트에서 `virt-fw-vars --add-db`로 VARS에 직접 주입 (python3-virt-firmware 기설치 환경이므로 즉시 가능 — 4.5 방법 2 참조).

## 5. 결론

로그 3,879건 중 오류·경고는 전부 위 4가지 계열로 수렴하며, **VM 고장이나 데이터 손상을 시사하는 항목은 전무**. 실사용 증상(멈춤, 재부팅 반복, 앱 오류 등)이 있는 경우 별도 관점의 재분석 필요.
